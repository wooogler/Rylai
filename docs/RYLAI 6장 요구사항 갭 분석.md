## 2. 최우선 갭 — 작업 스트림별 정리

### 🔴 A. 80% 보호적 응답 점수 체계 (문서의 핵심 메커니즘이 현재와 다름)

현재 구현과 명세가 **점수 공식, 명칭, 게이트 방식 세 가지 모두** 다릅니다. 6장에서 가장 반복적으로 등장하는 요구사항입니다 (L135, L137, L143, L146, L159, L161, L167, L171, L213–215, L243–245).

| 항목 | 명세 (6장) | 현재 구현 |
|---|---|---|
| 공식 | `protective / Max(20, protective+neutral+vulnerable)` | `protective / (protective+vulnerable)` — **neutral 제외, 20개 하한 없음** (`app/store/useScenarioStore.ts:60-74`) |
| 명칭 | "Protective Response Rate" | "Resilience" (`app/chat/[scenario]/page.tsx:825,828`) |
| 진행 게이트 | 80% 점수 도달 시 **축하 모달** ("Congratulations, you have reached 80%...") + 버튼 2개 (시나리오1: Continue Chatting / Next Scenario, 시나리오2: Continue Chatting / End Chat) | **연속 안전 응답 streak** (기본 5회 연속)이 조용히 Next 버튼 잠금 해제 — 모달·축하 문구·선택 버튼 없음 (`page.tsx:535-540, 688-692`) |
| 점수 저장 | 로깅 필수 (L248) | 클라이언트에서만 계산, **DB에 저장 안 됨** |
| 표시 조건 | 항상 | masteryEnabled가 **꺼져 있을 때만** Resilience 배지 표시 (`page.tsx:822`) |

**필요 작업**: `computeResilience` 공식 교체 → 명칭 전면 변경 → streak 게이트를 80% 점수 게이트로 대체(또는 병행 제거) → 시나리오별 축하 모달 2종 구현 → 점수의 서버 측 저장.

### 🔴 B. 참가자 온보딩 플로우 (Step 1–4: 19/23 항목 누락)

- **접근 코드(Access Code) 게이트 없음** — 현재 학습자는 username+password만으로 누구나 가입 가능. 연구진이 발급하는 참가자별 고유 코드(예: `p1-rylai`) 저장·검증 체계가 전혀 없음 (`app/api/auth/signup/route.ts:19-29` — 유일한 코드는 공유 `ADMIN_PASSCODE`이며 역할 구분 용도). 참고: 가입 후 로그인 페이지로 보내는 대신 **자동 로그인** 처리 중 (명세와 상이).
- **환영 화면(Welcome Screen) 전체 부재** — "What is RYLAI?", 2개 시나리오 안내, 목표 문구, 중도 철회 고지, "Let's Begin" 버튼 모두 없음. `welcome` 관련 코드 0건.
- **시나리오 스플래시 모달 부재** — 채팅 위에 뜨는 스크롤 가능한 모달(시나리오 소개 + 스테이지 설명 + 80% 규칙), 그리고 이를 편집할 **전용 마크다운 에디터**(관리자용) 모두 없음. DB에 스플래시 콘텐츠 컬럼 자체가 없음.
- **철회 고지 푸터 부재** — predator 챗봇이 있는 모든 페이지 하단에 "불이익 없이 중단 가능" 고지 필요 (L119). `app/layout.tsx`, 채팅 페이지 어디에도 없음.

### 🔴 C. 안전 종료 장치 (연구 윤리와 직결)

- **"I don't feel comfortable anymore." 버튼 없음** (L216) — 현재 채팅에서 나갈 방법은 Logout 또는 Reset뿐이며, 대화 중 자발적 종료 컨트롤이 없음 (`page.tsx:719-741`).
- **즉시 종료(safe exit) 조건 없음** (L203) — 참가자가 이탈/차단 시 상호작용을 즉시 끝내고 기록하는 메커니즘 부재.

### 🔴 D. 6.1b 평가 전용 챗봇 — 완전 미구현

스테이지를 구분하지 않는 자연 진행(natural progression) 모드, 종료 조건(약 100 메시지 / 30분 / 불편 종료) 모두 없음. 현재 `autoStage`+min1/max6로도 스테이지를 계속 추적·표시하므로 "스테이지를 구분하지 않는다"는 요건을 충족하지 못함. 별도 모드/플래그 신설 필요.

### 🟠 E. 시나리오 구조와 연속성

- **기본 시나리오가 명세와 다름**: 요구는 2개 시나리오(1–3단계 / 4–6단계, 둘 다 상대는 "Alex")이나, 현재는 3개 시나리오("The Friendly Gamer"(Alex), "The Supportive Friend"(Jordan), 3번째(Sam))이며 스테이지 범위 제약(min/max)도 기본값 1–6 (`lib/default-scenarios.ts:23-63`).
- **시나리오 1 히스토리 이월 + "3 months later" 구분선**: 이월 기능(`persistMessages`, `buildCarried`)은 존재하나 **기본 시나리오에서 꺼져 있고**, 시각적 "3 months later" 구분선은 미구현 (`page.tsx:200-239` — carried 메시지와 새 대화 사이에 구분자 없음).
- 명세의 정확한 시나리오 이름/설명 문구("Scenario 1: Meeting Someone New Online" 등)와 기본값 불일치.

### 🟠 F. 피드백 3파트 구조화 (6.2)

- 세 가지 내용(응답 평가 / 상대의 단계·의도 / 다음 대응)은 **한 덩어리 프로즈 안에 녹아** 있음. 현재 프롬프트가 오히려 "no headings, no bullet lists"로 **구조화를 금지** (`lib/feedback-prompts.ts:28-32`) — L240의 "콜론 구분 + 볼드 시각 구조화" 요구와 정반대.
- **3파트 개별 on/off 관리자 토글 없음**, **통합 메시지 vs 탭 표시 옵션 없음** (`FeedbackConfig`에 해당 필드 자체가 없음, `lib/db/schema.ts:9-13`).
- 분류 이유(rationale)는 연구자 전용으로만 기록되고 **참가자에게는 "왜 그렇게 분류됐는지" 표시되지 않음** (L235 미충족).
- **predator 응답 전 인위적 지연 없음** (L239) — 로봇처럼 즉시 응답.
- **80% 도달 알림 / 자기 성찰 유도 메시지 없음** (L244–245).

### 🟠 G. 교육자 전용 URL (L96–97)

`rylai.cs.vt.edu/main` 같은 교육자별 전용 경로 없음. 현재는 정반대로 **모든 학습자가 전체 교육자 목록에서 선택**하는 구조 (`/select-user`, `app/api/get-users-with-progress`가 전체 교육자를 노출). `app/[educator]` 동적 라우트 + 교육자 고정 컨텍스트 + 목록 노출 제거 필요.

### 🟡 H. 기타 확정 갭

- **호버 스테이지 표시 제거 필요** (L144, L169): `MessageBubble.tsx:57-126`에 메시지별 스테이지 호버 툴팁이 여전히 존재 — 피드백으로 통합하고 제거해야 함.
- **스테이지 전환 완급 조절(최소 5회 교환) 미보장** (L198): 앱 측 카운터가 없고 VT 서버에 전적으로 위임됨. `stageOverride`/`minStage`를 활용한 앱 측 게이트 또는 서버 측 보장 필요.
- **보호적 응답 → 스테이지 상승 방지 결합 없음** (L249): 피드백 분류 결과가 스테이지 전환에 반영되지 않음 — "보호 행동을 해도 소용없다"는 인상을 줄 위험.
- **로깅 공백** (L248): 메시지·피드백·분류·스테이지는 저장되지만 **점수와 진행 권고는 미저장**, 연구용 내보내기 엔드포인트 없음 (관리자 Export는 시나리오 설정만 포함).
- **교육자 화면 정리 요청 미반영** (L180–181): 문서가 "불필요"라고 한 'Require mastery' 체크박스와 '이전 시나리오 이어가기' 체크박스가 여전히 존재하고, Starting/Minimum Stage 중복 필드도 그대로.

## 3. ⚠️ 요구사항 문서 내부의 모순 (팀 확인 필요)

분석 중 문서 자체의 충돌 2건이 발견되었습니다. 구현 전에 연구팀과 정리가 필요합니다.

1. **L181 vs L168/L210**: 교육자 플로우 절은 "이전 시나리오의 대화 이어가기 필드는 불필요 — 두 시나리오는 독립적인 채팅 인스턴스"라고 하는 반면, 청소년 플로우 Step 7과 6.1a는 "시나리오 1의 대화 기록을 가져와 '3 months later' 구분선 후 새 대화 시작"을 요구합니다. → 해석: **표시(UI)상으로는 이월 + 구분선, 채팅 세션(VT)은 독립**이 의도로 보이나, 교육자 설정에서 토글을 제거하면 이 동작을 어디서 제어할지 결정 필요.
2. **L146/L159 "80% 도달 후에도 계속 대화 가능" vs streak 기반 mastery**: 최근 구현된 mastery 게이트(연속 응답 기반)는 문서의 80% 점수 게이트와 설계 철학이 다릅니다(문서: 비율 기반, 20개 하한 / 구현: 연속성 기반). 둘을 병행할지, streak을 완전히 대체할지 결정 필요.

## 5. 구현 우선순위 제안

연구(공동 설계 스터디) 실행에 필수적인 순서 기준:

1. **점수 체계 정합화** (2-A) — 공식·명칭·80% 모달·점수 저장. 다른 다수 항목(스플래시 문구, 알림, 로깅)의 전제 조건.
2. **참가자 온보딩** (2-B) — Access Code 게이트 → 환영 화면 → 스플래시 모달 (+ 관리자 마크다운 에디터 2종). 참가자 통제와 IRB 관점에서 필수.
3. **안전 종료** (2-C) — "I don't feel comfortable anymore." 버튼 + 철회 고지 푸터. 윤리 요건.
4. **시나리오 재편** (2-E) — 기본 2개 시나리오(1–3/4–6, Alex 연속), persistMessages 기본 활성 + "3 months later" 구분선.
5. **피드백 구조화** (2-F) — 3파트 라벨 출력 + 토글/표시 옵션 + 응답 지연.
